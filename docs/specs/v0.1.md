# Marea — Especificaciones técnicas
## Versión 0.1 — Foundation Release

**Estado:** Borrador consolidado para implementación  
**Producto:** Marea — Shared Trips & Adventures  
**Objetivo:** establecer una base funcional, segura y modular para que un grupo de colaboradores pueda continuar desarrollando Marea.

---

## 1. Resumen del producto

Marea es una aplicación web colaborativa para organizar escapadas, viajes grupales y expediciones de pesca. A largo plazo podrá incluir agenda de viajes, votaciones, asistencia, checklists, tareas y gastos compartidos.

La versión 0.1 se limita a:

1. Autenticación mediante Clerk.
2. Autorización de acceso mediante un registro interno en PostgreSQL.
3. Un calendario compartido de solo lectura.
4. Una API mínima con FastAPI.
5. Un modelo persistente inicial para usuarios y eventos.
6. Una base de desarrollo documentada, migraciones y pruebas.

La versión no implementará las funcionalidades de organización de viajes.

## 2. Objetivos y definición de éxito

### Objetivos

- Permitir que usuarios autorizados inicien sesión mediante Clerk.
- Impedir que usuarios no autorizados consulten el calendario.
- Mostrar una vista mensual de calendario con navegación entre meses.
- Consultar eventos precargados en PostgreSQL.
- Mantener separadas la interfaz, la API, la lógica de autorización y la persistencia.
- Permitir que otro desarrollador clone el repositorio y ejecute el proyecto siguiendo el README.

### Criterio general de éxito

Un usuario autorizado puede iniciar sesión y consultar los eventos del calendario. Un usuario sin sesión o autenticado pero no autorizado no puede consultar los datos protegidos. La aplicación no ofrece funciones para crear, editar ni eliminar eventos.

## 3. Alcance

### Incluido

- Clerk: registro/inicio de sesión y cierre de sesión.
- Rutas privadas en frontend.
- Validación del token de Clerk en FastAPI.
- Registro interno mínimo del usuario y estado de autorización.
- Calendario mensual de solo lectura.
- Navegación entre meses.
- Consulta de eventos por intervalo.
- Estados de carga, error y calendario vacío.
- PostgreSQL, SQLAlchemy y Alembic.
- Seed idempotente de eventos de ejemplo.
- Pruebas automatizadas básicas.
- Configuración local y documentación.

### Excluido

- Crear, editar o eliminar eventos desde la aplicación.
- Votaciones, RSVP, viajes, destinos y participantes.
- Grupos y permisos configurables por grupo.
- Checklists, tareas, gastos y liquidaciones.
- Notificaciones propias de Marea.
- Chat o colaboración en tiempo real.
- Integración con Google Calendar u otros calendarios externos.
- Carga de archivos, MinIO/Garage y almacenamiento de objetos.
- Redis.
- Aplicación móvil.
- Panel administrativo completo.
- Despliegue remoto como requisito de v0.1.

Los datos del calendario son de solo lectura desde la aplicación y su API. Un seed puede insertar datos iniciales y un administrador técnico puede modificar la base de datos directamente fuera de la aplicación.

## 5. Arquitectura

### Frontend

Responsabilidades:
- Renderizar el calendario y la navegación.
- Integrar Clerk para autenticación.
- Enviar tokens de sesión en las solicitudes al backend.
- Mostrar estados de carga, error y acceso denegado.
- No asumir que ocultar una página equivale a proteger los datos.

### Clerk

Responsabilidades:
- Gestionar credenciales y sesiones.
- Proporcionar al frontend una sesión y los tokens correspondientes.
- Ser la fuente de identidad externa del usuario.

Clerk no decide por sí solo si una cuenta tiene permiso para entrar al calendario de Marea. Esa decisión corresponde a la autorización interna.

### Backend

Responsabilidades:
- Verificar tokens de Clerk, incluyendo firma, emisor y expiración, usando el método oficial compatible con la configuración de Clerk.
- Resolver la identidad externa.
- Consultar el estado de autorización en PostgreSQL.
- Rechazar usuarios sin acceso activo.
- Servir los eventos del calendario por medio de endpoints de solo lectura.
- Validar los parámetros de las solicitudes.

### PostgreSQL

Responsabilidades:
- Guardar el registro interno de usuarios y su estado de acceso.
- Guardar los eventos del calendario.
- Mantener restricciones de integridad.
- Recibir cambios de estructura mediante migraciones de Alembic.

### Principio arquitectónico

Se utilizará un monolito modular. No se crearán servicios independientes ni módulos vacíos para funcionalidades futuras.

## 7. Modelo de datos

### 7.1 User

Representa al usuario interno de Marea asociado a una identidad de Clerk.

Campos propuestos:
- `id`: UUID, clave primaria.
- `clerk_user_id`: texto único y no nulo.
- `email`: opcional; guardar solo si existe una necesidad concreta.
- `access_status`: `pending`, `active` o `revoked`.
- `created_at`: fecha de creación.
- `updated_at`: última modificación.

Restricciones:
- `clerk_user_id` debe ser único.
- La cuenta en Clerk no otorga acceso automáticamente.
- La autorización se verifica en el backend para cada solicitud protegida.

### 7.2 CalendarEvent

Representa un evento visible en el calendario.

Campos propuestos:
- `id`: UUID, clave primaria.
- `title`: texto obligatorio.
- `description`: texto opcional.
- `starts_at`: timestamp con zona horaria.
- `ends_at`: timestamp con zona horaria.
- `created_at`: fecha de creación del registro.

Restricciones:
- `ends_at` debe ser posterior a `starts_at`.
- Las fechas deben almacenarse de forma coherente, preferentemente en UTC.
- El calendario debe convertirlas a la zona horaria de presentación elegida.
- No se exponen operaciones HTTP de escritura en v0.1.

### 7.3 Entidades futuras

No crear todavía tablas para `Group`, `GroupMember`, `Trip`, `DateProposal`, `Attendance`, `ChecklistItem`, `Expense` o `ExpenseShare`.

## 8. Requisitos funcionales verificables

### AUTH-001 — Autenticación
El usuario podrá iniciar sesión mediante Clerk.
- Una sesión válida permite iniciar el flujo de acceso privado.
- Marea no almacena contraseñas.
- El cierre de sesión finaliza la sesión de Clerk.

### AUTH-002 — Protección de frontend
Las páginas privadas requieren sesión.
- Sin sesión, el usuario es enviado al flujo de inicio de sesión.
- El frontend muestra un estado comprensible cuando el usuario no tiene acceso.

### AUTH-003 — Validación de token
FastAPI verifica el token recibido.
- Tokens ausentes, expirados, con firma inválida o emisor incorrecto son rechazados.
- No basta con decodificar el JWT; se debe verificar su validez criptográfica.

### AUTH-004 — Autorización interna
El backend verifica el estado del usuario en PostgreSQL.
- `active`: permite consultar el calendario.
- `pending`: deniega el acceso.
- `revoked`: deniega el acceso.
- Un usuario de Clerk sin registro interno no obtiene acceso automáticamente.

### AUTH-005 — Identidad
El backend identifica al usuario a partir del token verificado, no de un `user_id` arbitrario enviado en el cuerpo o en parámetros de la solicitud.

### CAL-001 — Vista mensual
- Se muestra mes y año.
- Se puede navegar al mes anterior y al siguiente.
- La cuadrícula representa correctamente los días.
- La interfaz es utilizable en escritorio y móvil.

### CAL-002 — Consulta de eventos
- Los eventos se obtienen de PostgreSQL.
- La consulta solicita un intervalo temporal.
- Solo usuarios autenticados y autorizados pueden consultar eventos.
- Se muestran los eventos en sus fechas correspondientes.

### CAL-003 — Solo lectura
- No hay controles para crear, editar o borrar eventos.
- La API no expone `POST`, `PUT`, `PATCH` ni `DELETE` para eventos.
- Las solicitudes de escritura no están implementadas.

### CAL-004 — Calendario vacío
- El calendario sigue mostrando la cuadrícula cuando no hay eventos.
- Se informa que no existen eventos en el período.
- Una lista vacía no se trata como error.

### CAL-005 — Estados de interfaz
- Se muestra carga durante la consulta.
- Los errores se comunican sin mostrar secretos ni trazas.
- Se permite reintentar una consulta fallida.

## 9. API inicial

Prefijo: `/api/v1`.

### `GET /health`
Comprueba que el proceso de API está activo. No devuelve información sensible. La comprobación de salud de la base de datos, si se necesita, deberá definirse explícitamente.

Respuesta:
```json
{"status": "ok"}
```

### `GET /api/v1/users/me`
Requiere token válido de Clerk. Devuelve la identidad interna y el estado de acceso del usuario autenticado. No permite consultar arbitrariamente a otro usuario.

### `GET /api/v1/calendar/events?start={datetime}&end={datetime}`
Requiere autenticación y autorización.
- Valida que `start` y `end` sean fechas válidas.
- Rechaza un intervalo vacío o invertido.
- Devuelve los eventos del intervalo solicitado.
- El límite del intervalo debe documentarse y probarse.
- No admite operaciones de escritura.

Respuesta conceptual:
```json
{
  "items": [
    {
      "id": "uuid",
      "title": "Salida de pesca",
      "description": null,
      "starts_at": "2026-11-14T08:00:00Z",
      "ends_at": "2026-11-14T18:00:00Z"
    }
  ]
}
```

El evento del ejemplo es ilustrativo y no implica que exista en los datos iniciales.

### Códigos de error
- `400 Bad Request`: parámetros inválidos, si se usa validación manual.
- `401 Unauthorized`: token ausente o no válido.
- `403 Forbidden`: identidad válida sin autorización.
- `422 Unprocessable Entity`: solicitud que no supera la validación automática de FastAPI.
- `500 Internal Server Error`: error no controlado, sin filtrar detalles internos.

La implementación debe evitar inconsistencias innecesarias entre `400` y `422` y documentar el contrato final.

## 10. Seguridad

- Validar tokens de Clerk con el mecanismo oficial configurado.
- Verificar firma, emisor, expiración y audiencia cuando corresponda.
- Comprobar autorización en el backend para cada endpoint protegido.
- No registrar tokens completos ni secretos en logs.
- No almacenar secretos en el repositorio.
- Mantener secretos del servidor fuera de las variables públicas de Vite.
- Restringir CORS a los orígenes configurados.
- Usar consultas parametrizadas y SQLAlchemy.
- No devolver trazas internas al usuario.
- Denegar por defecto cuando no pueda comprobarse la autorización.

## 11. Seed de eventos

Los eventos iniciales se insertarán mediante un comando de seed separado de las migraciones estructurales.

Requisitos:
- El seed debe ser idempotente: ejecutarlo repetidamente no duplica los mismos eventos.
- Cada evento de prueba debe tener un identificador estable o una clave de referencia adecuada.
- Los datos deben incluir títulos y fechas realistas para probar distintos meses.
- Las fechas se almacenan con zona horaria coherente.
- La API solo ofrece lectura.
- Los cambios al conjunto de datos de desarrollo se documentan en el repositorio.

Las migraciones de Alembic definen la estructura de las tablas. El seed inserta datos de prueba; ambos procesos cumplen funciones distintas.

## 12. Inicialización del entorno local

Los comandos siguientes son una guía para el bootstrap inicial. Ejecutarlos desde la raíz del repositorio, salvo donde se indique. Los detalles pueden variar según el sistema operativo.

### 12.1 Requisitos previos

Instalar:
- Git.
- Node.js en una versión LTS compatible con Vite y npm.
- Python en una versión compatible con la versión de FastAPI elegida.
- `uv` para administrar el entorno Python y sus dependencias.
- Docker y Docker Compose, recomendados para ejecutar PostgreSQL localmente.

Verificar instalaciones:
```bash
git --version
node --version
npm --version
python --version
uv --version
docker --version
docker compose version
```

### 12.2 Crear el repositorio

```bash
mkdir marea
cd marea
git init
mkdir -p apps docs/specs
```

Crear un `.gitignore` que excluya al menos:
```gitignore
.env
.env.*
!.env.example
node_modules/
dist/
.venv/
__pycache__/
.pytest_cache/
.mypy_cache/
.ruff_cache/
*.py[cod]
```

Ajustar las excepciones de `.env.example` según la herramienta y el sistema de despliegue que se elija.

### 12.3 Inicializar React, Vite y TypeScript

Desde la raíz del repositorio:
```bash
npm create vite@latest apps/web -- --template react-ts
cd apps/web
npm install
npm run dev
```

Vite mostrará una URL local, normalmente `http://localhost:5173`. Confirmar que la página inicial se renderiza y detener el servidor antes de continuar.

Instalar Tailwind CSS siguiendo la guía de instalación correspondiente a la versión elegida. Añadir Radix UI y Lucide React cuando se implementen componentes que los necesiten. No es necesario instalar todas las bibliotecas de Radix si solo se utilizan algunas.

Instalar Clerk para React con el SDK oficial de Clerk para React y configurar el proveedor de autenticación en el punto de entrada. La clave publicable de Clerk puede estar en una variable de frontend como `VITE_CLERK_PUBLISHABLE_KEY`; nunca colocar la clave secreta de Clerk en variables `VITE_*`.

Configurar las URLs permitidas y los redirects de Clerk para el entorno local.

### 12.4 Inicializar FastAPI y el entorno Python

Desde la raíz:
```bash
cd apps/api
uv init --package
uv add fastapi "uvicorn[standard]" sqlalchemy alembic psycopg[binary] pydantic-settings
uv add --dev pytest httpx ruff
```

Si `uv init --package` genera una estructura distinta a la prevista, adaptarla conservando un único punto de entrada claro. Crear el paquete de aplicación y los módulos a medida que se implementen.

Iniciar el servidor:
```bash
uv run uvicorn app.main:app --reload
```

El módulo `app.main` debe exponer una instancia `app = FastAPI()`. Al estar configurado correctamente, FastAPI publica documentación interactiva en `/docs` y el esquema OpenAPI.

No se debe asumir que el backend ya funciona solo por instalar dependencias: primero hay que crear el módulo de entrada y el endpoint `/health`.

### 12.5 Inicializar PostgreSQL con Docker Compose

Crear `compose.yaml` en la raíz con un servicio PostgreSQL. Ejemplo inicial para desarrollo local:

```yaml
services:
  db:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_DB: marea
      POSTGRES_USER: marea
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Define POSTGRES_PASSWORD en el entorno}
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U marea -d marea"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  postgres_data:
```

La versión de PostgreSQL debe fijarse conscientemente y mantenerse documentada. El ejemplo usa PostgreSQL 17 como una versión explícita de desarrollo; se puede elegir otra versión soportada si el equipo lo prefiere.

Crear una contraseña local mediante una variable de entorno, sin subirla al repositorio. Después ejecutar desde la raíz:
```bash
docker compose up -d db
docker compose ps
docker compose logs db
```

La publicación del puerto queda limitada a `127.0.0.1`, para no exponer la base de datos a la red local por defecto.

Configurar una URL de conexión en el entorno de FastAPI, por ejemplo:
```text
DATABASE_URL=postgresql+psycopg://marea:CONTRASEÑA@localhost:5432/marea
```

Sustituir la contraseña por la definida localmente. Si contiene caracteres reservados de URL, debe codificarse correctamente. No guardar la URL real con credenciales en el repositorio.

### 12.6 Configurar SQLAlchemy y Alembic

Crear:
- Una configuración central para cargar variables de entorno.
- Un motor SQLAlchemy.
- Una fábrica de sesiones.
- Una clase base para modelos.
- Los modelos `User` y `CalendarEvent`.

Desde `apps/api`:
```bash
uv run alembic init alembic
```

Si el comando crea archivos o directorios que ya existan, integrar la configuración sin sobrescribir trabajo previo.

Configurar `alembic.ini` y `alembic/env.py` para:
- Leer la URL de base de datos desde la configuración de la aplicación.
- Importar los modelos de SQLAlchemy.
- Exponer `Base.metadata` como `target_metadata`.
- Evitar almacenar contraseñas en el archivo versionado.

Crear la primera migración:
```bash
uv run alembic revision --autogenerate -m "create users and calendar events"
```

Revisar el archivo generado antes de aplicarlo. La generación automática puede omitir o interpretar incorrectamente algunos cambios; siempre hay que inspeccionar la migración.

Aplicar las migraciones:
```bash
uv run alembic upgrade head
```

Verificar el estado:
```bash
uv run alembic current
uv run alembic history
```

No crear tablas manualmente en producción o desarrollo como sustituto de las migraciones versionadas.

### 12.7 Crear y ejecutar el seed

Implementar un comando explícito, por ejemplo:
```bash
uv run python -m app.db.seed
```

El comando debe:
- Abrir una sesión SQLAlchemy.
- Insertar eventos de ejemplo si todavía no existen.
- Ser idempotente.
- Cerrar correctamente la sesión.
- Informar cuántos registros insertó o si no había cambios.

No mezclar este comando con `alembic upgrade head`.

### 12.8 Variables de entorno

Mantener archivos de ejemplo sin secretos reales.

`apps/web/.env.example`:
```dotenv
VITE_CLERK_PUBLISHABLE_KEY=
VITE_API_BASE_URL=http://localhost:8000
```

`apps/api/.env.example`:
```dotenv
APP_ENV=development
DATABASE_URL=postgresql+psycopg://marea:CHANGE_ME@localhost:5432/marea
CLERK_JWKS_URL=
CLERK_ISSUER=
CLERK_AUTHORIZED_PARTY=
CORS_ORIGINS=http://localhost:5173
```

Los nombres definitivos de las variables de Clerk deberán corresponder al método oficial de verificación elegido. No implementar una validación JWT casera ni aceptar variables sin comprobar su significado. Si se utiliza el SDK oficial de Clerk para verificar tokens, configurar los valores que ese SDK requiera.

La clave secreta de Clerk, si el flujo elegido la requiere, pertenece únicamente al entorno del backend. Nunca debe utilizarse como una variable `VITE_*`.

### 12.9 Ejecutar el proyecto localmente

En una terminal:

## 13. Pruebas y calidad

- Token ausente o inválido → `401`.
- Token válido con usuario sin acceso → `403`.
- Usuario activo → acceso permitido.
- Usuario revocado → acceso denegado.
- Consulta de eventos con intervalo válido.
- Rechazo de intervalos inválidos.
- Seed ejecutado dos veces sin duplicados.
- No existen endpoints de escritura de eventos.

### Pruebas frontend
- Renderizado del calendario.
- Navegación de meses.
- Estado de carga.
- Estado de error.
- Estado vacío.
- Acceso a rutas protegidas.
- Presentación de acceso denegado.

### Comandos de calidad
Documentar en el README los comandos de instalación, ejecución, pruebas y lint. Mantener las pruebas independientes de credenciales personales reales.

## 15. Decisiones pendientes

### DEC-003 — Alta de usuarios internos
Definir cómo se crea el registro interno cuando un usuario se autentica por primera vez. La creación de una cuenta Clerk no debe habilitar automáticamente el acceso. Para v0.1 puede usarse un comando administrativo local o una operación controlada.

### DEC-004 — Sincronización de perfil
No está definida la sincronización de nombre, avatar y correo entre Clerk y PostgreSQL. No bloqueará la primera implementación. Guardar únicamente los datos necesarios y evitar replicar datos de Clerk sin una necesidad funcional.

### DEC-005 — Componente visual

### DEC-006 — Despliegue

## 16. Plan de implementación

1. **Bootstrap:** crear monorepo, frontend, backend y PostgreSQL.
2. **Persistencia:** configurar SQLAlchemy, modelos, Alembic y seed.
3. **Autenticación:** integrar Clerk en React y validar tokens en FastAPI.
4. **Autorización:** implementar el estado interno de acceso y el mecanismo de habilitación inicial.
5. **Calendario:** implementar la vista mensual, endpoint de consulta y estados de interfaz.
6. **Calidad:** ejecutar pruebas, revisar permisos y completar el README.
7. **Entrega:** comprobar todos los criterios de aceptación y etiquetar la versión `v0.1.0`.

## 17. Principio de evolución

Marea v0.1 debe ser pequeña, funcional y fácil de entender. La arquitectura modular existe para mantener responsabilidades claras, no para anticipar todas las funcionalidades futuras.

Las próximas features se incorporarán mediante requisitos verificables, cambios explícitos al modelo de datos, migraciones y contratos de API. No se agregarán Redis, almacenamiento de archivos, grupos ni lógica de gastos hasta que exista una necesidad concreta.
